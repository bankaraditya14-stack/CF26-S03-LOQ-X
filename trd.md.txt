# TRD — Urban Infrastructure Cascade Simulator (S-03)

**Defines HOW the product described in `02_PRD.md` will be implemented.**

---

# 1. Technical Objective

Build a deterministic, browser-based simulation engine that models
urban infrastructure as a directed dependency graph and simulates
failure propagation, recovery, and measurable impact over simulated
time.

The system must be:

- Deterministic
- Explainable
- Reproducible
- Modular
- Fast enough for real-time demo playback
- Independent from real municipal infrastructure

The first implementation will use synthetic infrastructure data.

---

## Frontend

## Visualization

- React Flow for the infrastructure dependency graph

Use React state/hooks initially.

Do not introduce Redux or another global state library unless
implementation complexity requires it.

## Persistence

Use browser localStorage for saved scenarios and simulation history.

No backend is required for the MVP.

5. Node Model

Each infrastructure service is represented as a node.

type NodeStatus =
  | "HEALTHY"
  | "AT_RISK"
  | "DEGRADED"
  | "FAILED"
  | "RECOVERING";

Example:

interface InfrastructureNode {
  id: string;
  name: string;
  type: ServiceType;
  status: NodeStatus;

  criticality: "LOW" | "MEDIUM" | "HIGH";

  zone: string;

  recoveryTime: number;

  position: {
    x: number;
    y: number;
  };
}

Example node:

{
  id: "water-pump-01",
  name: "Central Water Pump",
  type: "WATER_PUMP",
  status: "HEALTHY",
  criticality: "HIGH",
  zone: "Central",
  recoveryTime: 8,
  position: { x: 400, y: 200 }
}

7. Dependency Model

Dependencies are directed edges.

interface DependencyEdge {
  id: string;

  source: string;
  target: string;

  propagationDelay: number;

  dependencyType:
    | "POWER"
    | "NETWORK"
    | "WATER"
    | "OPERATIONAL";

  failureImpact: "DEGRADE" | "FAIL";
}

Example:

Power Grid
     │
     ▼
Water Pump
     │
     ▼
Water Distribution
     │
     ▼
Hospital

This means failure can propagate downstream.

8. Simulation Clock

The simulation uses a virtual clock.

It must NOT depend on real-world time.

Example:

T+00 min
T+05 min
T+10 min
T+15 min

The engine advances time by processing scheduled events.

Controls:

▶ Play
⏸ Pause
⏭ Step
↻ Reset
1x / 2x / 4x speed
9. Event Model

Every state transition is represented as an event.

interface SimulationEvent {
  id: string;

  timestamp: number;

  type:
    | "FAILURE_INJECTED"
    | "STATE_CHANGED"
    | "FAILURE_PROPAGATED"
    | "RECOVERY_STARTED"
    | "RECOVERY_COMPLETED";

  sourceNode?: string;

  targetNode: string;

  previousState: NodeStatus;

  newState: NodeStatus;

  cause?: string;
}

Example:

T+00  Power Grid FAILED
T+05  Water Pump FAILED
T+10  Water Distribution DEGRADED
T+15  Hospital DEGRADED

The event log is the primary source for the timeline and
explainability UI.

10. Event Queue

The engine uses a deterministic priority queue.

Events are ordered by:

Simulation timestamp
Event priority
Stable event ID

Example:

Event Queue

T+05  Water Pump failure
T+05  Telecom degradation
T+10  Water Distribution failure
T+12  Emergency Dispatch degradation

Same-timestamp events must always be processed in the same order.

This guarantees reproducibility.

11. Failure Injection

The user can select one or more initial failures.

Example:

Initial Failures:

☑ Power Grid
☑ Telecom

Simulation Start

All initial failures occur at:

T+00

The engine creates one initial event for each selected node.

12. Failure Propagation Algorithm

When a node fails:

Find all downstream nodes.
Check their dependency states.
Determine the resulting state.
Schedule the state transition using the configured propagation delay.
Add the transition to the event queue.
Continue until no new downstream transitions are produced.

Example:

Power Grid FAILED
        ↓ +5 min
Water Pump FAILED
        ↓ +5 min
Water Distribution FAILED
        ↓ +5 min
Hospital DEGRADED
13. Multiple Simultaneous Failures

Multiple failures occurring at the same timestamp must be processed
as one simulation batch.

Example:

T+00

Power Grid FAILED
Telecom FAILED

If both affect Emergency Dispatch:

Power Grid ─────┐
                ├──> Emergency Dispatch
Telecom ────────┘

Emergency Dispatch must receive one combined state evaluation.

It must NOT be counted twice.

14. Multi-Dependency Rule

For the MVP, the worst dependency state determines the resulting
state.

Example:

Power = FAILED
Telecom = HEALTHY

Result:

Emergency Dispatch = DEGRADED

If:

Power = FAILED
Telecom = FAILED

Result:

Emergency Dispatch = FAILED

This rule is deterministic and easy to explain during the demo.

15. State Transition Rules
HEALTHY → AT_RISK

A dependency becomes degraded or unavailable but the node can
temporarily continue operating.

AT_RISK → DEGRADED

Dependency disruption persists beyond the configured threshold.

DEGRADED → FAILED

Required dependency remains unavailable beyond the failure threshold.

FAILED → RECOVERING

A recovery action is initiated.

RECOVERING → HEALTHY

Configured recovery duration completes.

The MVP must not allow:

FAILED → HEALTHY

without passing through:

RECOVERING
16. Recovery Manager

The system supports recovery actions.

MVP actions:

REPAIR
BACKUP_POWER
RESTORE_NETWORK
ISOLATE_SERVICE

Example:

Power Grid FAILED
        ↓
Backup Power activated
        ↓
Hospital RECOVERING
        ↓
Hospital HEALTHY

Recovery actions must create events in the event log.

17. Metrics Engine

The engine calculates three mandatory metrics.

Cascade Depth

Longest dependency path reached by the cascade.

Example:

Power
 ↓
Water Pump
 ↓
Water Distribution
 ↓
Hospital

Cascade Depth = 3

Initial failure has depth 0.

Affected Services

Count of downstream services that entered a non-healthy state.

Initial failed nodes are excluded.

Example:

Initial:
Power

Affected:
Water Pump
Water Distribution
Hospital

Affected Services = 3
Recovery Time

Time between failure and successful recovery.

Example:

Hospital FAILED at T+15
Hospital HEALTHY at T+35

Recovery Time = 20 minutes
18. Explainability Engine

Every non-healthy state should have a causal explanation.

Example:

Why is Hospital degraded?

Because:
Power Grid failed at T+00
        ↓
Water Pump failed at T+05
        ↓
Water Distribution failed at T+10
        ↓
Hospital degraded at T+15

The engine should store the causal parent/event reference.

22. Reproducibility

The engine must avoid:

Math.random()

or any other uncontrolled randomness.

Example:

     ↓
Event Log X

Scenario A
     ↓
Run 2
     ↓
Event Log X

Both logs must be identical.

interface SimulationEngine {

The application must gracefully handle:

Missing node
Invalid dependency
Duplicate node IDs

Example:

A → B

The scenario should be marked invalid instead of causing an infinite

35. Final Technical Principle

The system should follow:

INPUT
  ↓
Scenario
  ↓
Deterministic Simulation Engine
  ↓
Events + State Changes
  ↓
Metrics + Causal Explanation
  ↓
Visualization

The UI must never become the source of truth.

Simulation state and event history are the source of truth.


## Deterministic Event Processing

The simulation engine shall use a deterministic event queue.

Events shall be ordered by:

1. simulated timestamp
2. event priority/type
3. stable event identifier

The engine must not use `Math.random()`, `Date.now()`,
network-dependent values, or UI rendering order to determine
simulation results.


## Engine/UI Separation

The simulation engine must not depend on:

- React components
- React Flow
- DOM APIs
- browser rendering state

React UI communicates with the engine through a controller/hook layer.

The engine remains responsible for simulation truth.


## Testing Requirements

The engine should include tests for:

- single failure propagation
- multi-hop cascade
- simultaneous failures
- shared dependency handling
- recovery
- repeated recovery/failure
- cascade depth calculation
- affected-service calculation
- recovery-time calculation
- scenario replay determinism
- circular dependency rejection
