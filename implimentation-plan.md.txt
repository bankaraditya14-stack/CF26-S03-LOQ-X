# Implementation Plan — Urban Infrastructure Cascade Simulator (S-03)

This document converts the PRD, TRD, Architecture, UI/UX, Test Plan,
and Data Model into an executable development plan.

The project will be developed in small verified stages.

Core principle:

> Build the simulation engine first, connect the UI second, add visual
> polish only after the core system is correct.

---

# 1. Development Strategy

The implementation will follow this order:

```text
Project Setup
      ↓
Data Model
      ↓
Graph Engine
      ↓
Simulation Engine
      ↓
Event System
      ↓
Cascade Propagation
      ↓

      ↓

      ↓

      ↓
API / State Integration
      ↓
Main UI
      ↓
Graph Visualization
      ↓
Timeline + Inspector
      ↓
Polish
      ↓
Testing
      ↓

The simulation engine must remain independent from the visual layer.

2. MVP Boundary

The MVP must demonstrate all core requirements from the problem statement:

Dynamic infrastructure graph
Time-dependent state
Failure propagation
Multiple simultaneous disruptions
Failure recovery
Cascade depth
Affected services
Recovery time
Reproducible scenarios

Everything else is secondary.

5. Phase 3 — Synthetic City Graph
Objective

Create the initial synthetic infrastructure graph.

Target:

10–15 nodes

Example:

Power Grid
Water Pump
Water Distribution
Telecom
Traffic Signals
Emergency Dispatch
Hospital
Sewage System
Public Transport
Fuel Station
Municipal Control

Example dependency graph:

                    POWER GRID
                   /    |     \
                  ↓     ↓      ↓
             WATER    TRAFFIC  SEWAGE
              PUMP     SIGNAL
                ↓
          WATER DISTRIBUTION
                ↓
             HOSPITAL
                ↑
        EMERGENCY DISPATCH
                ↑
             TELECOM

All infrastructure is synthetic.

No real municipal dependency should be claimed.

Acceptance:

Graph loads successfully.
Every edge references valid nodes.
No duplicate IDs.
Graph validation succeeds.
6. Phase 4 — Graph Validation
Objective

Validate scenario definitions before simulation starts.

Validation checks:

Duplicate node
Missing node reference
Invalid edge
Invalid delay
Invalid state
Circular dependency
Invalid scenario

Example:

Power → Water → Hospital → Power

should produce:

Circular dependency detected.

Acceptance:

Invalid graphs cannot start simulation.

7. Phase 5 — Simulation State
Objective

Create the runtime state of the graph.

Initial state:

All nodes = HEALTHY
Current time = 0
Event history = []
Metrics = 0

The engine must create a fresh runtime state for every simulation run.

Important:

Original Scenario
       ↓
Create Runtime State

Never mutate the original scenario.

8. Phase 6 — Event Engine
Objective

Create the deterministic event-processing system.

Basic structure:

Event Queue
     ↓
Get earliest event
     ↓
Advance simulation time
     ↓
Process event
     ↓
Update state
     ↓
Schedule new events
     ↓
Record event
     ↓
Repeat

Events must be ordered deterministically.

Example:

T+0  Power failure
T+5  Water Pump failure
T+10 Water Distribution degraded
T+15 Hospital degraded
9. Phase 7 — Failure Injection
Objective

Allow the user to introduce initial disruptions.

Single failure:

Power Grid → FAILED at T+0

Multiple failures:

Power Grid → FAILED at T+0
Telecom → FAILED at T+0

Multiple failures occurring at the same timestamp must be processed as one
logical batch.

Acceptance:

Initial failure is recorded.
State becomes FAILED.
Event appears in timeline.
Simulation starts from T+0.
10. Phase 8 — Cascade Propagation
Objective

Implement the core problem-solving logic.

When a node fails:

Find outgoing dependencies
        ↓
Check dependent node
        ↓
Schedule propagation event
        ↓
Apply state transition
        ↓
Continue downstream

Example:

Power Grid
     ↓
Water Pump
     ↓
Water Distribution
     ↓
Hospital

Power failure should propagate through the configured graph.

The propagation delay must come from scenario configuration.

11. Phase 9 — Multiple Failure Handling
Objective

Correctly handle multiple simultaneous disruptions.

Example:

Power Grid ─────┐
                ↓
            Emergency
            Dispatch
                ↑
Telecom ────────┘

At T+0:

Power = FAILED
Telecom = FAILED

Emergency Dispatch must be evaluated correctly without duplicate events.

Acceptance:

Emergency Dispatch

appears only once in affected-service metrics.

12. Phase 10 — State Transition Rules

Implement deterministic state transitions.

Example:

HEALTHY
   ↓
AT_RISK
   ↓
DEGRADED
   ↓
FAILED

Recovery:

FAILED
   ↓
RECOVERING
   ↓
HEALTHY

The exact transition logic must remain centralized in the simulation
engine.

Do not implement state logic separately inside UI components.

13. Phase 11 — Metrics Engine
Objective

Calculate required hackathon metrics.

Cascade Depth

Longest causal path from an initial failure.

Example:

Power
 ↓
Pump
 ↓
Water
 ↓
Hospital

Result:

Cascade Depth = 3
Affected Services

Count downstream nodes that became non-healthy.

Initial failure is excluded.

Recovery Time

Calculate simulated recovery duration according to the metric definition
locked in the PRD.

Acceptance:

Metrics must match the event history.

14. Phase 12 — Recovery System

Example:

16. Phase 14 — Replay System
Objective

Allow the user to replay an identical scenario.

Flow:

      ↓

Run Again
      ↓

Expected:

No random behavior should affect the result.

33. Scope Control Rule

If development time becomes limited:

Remove features in this order:

1. Decorative 3D
2. AI summary
3. Advanced animations
4. Scenario comparison
5. Advanced styling

Never remove:

Simulation Engine
Failure Propagation
Multiple Failures
Recovery
Metrics
Timeline
Replay

The core simulation is the project.
