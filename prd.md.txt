# 1. Product Vision

## One-line Vision

> A deterministic and explainable simulator that shows how failures
> propagate across interconnected urban services over time and how
> recovery actions can reduce the impact of a cascade.

## Product Positioning

The system is not a conventional monitoring dashboard.

A monitoring dashboard tells an operator:

> "Power is down."

Our system answers:

> "Power failed at T+0. Because the water pump depends on power,
> it degraded at T+5. The water network then degraded at T+10,
> affecting the hospital at T+15."

The product therefore acts as a:

**Mission Control for Urban Infrastructure Resilience.**

---

# 2. Problem

Urban infrastructure systems are interconnected.

Electricity, water, telecommunications, emergency services,
transportation and healthcare can depend on one another.

A failure in one service can therefore propagate into other services.

Traditional isolated monitoring can identify individual failures,
but does not necessarily explain:

- Which services will be affected?
- Through which dependency?
- When will the impact occur?
- How deep will the cascade become?
- Which recovery action can reduce the impact?

The simulator addresses this problem by representing the services
and their dependencies as a dynamic graph and simulating failure
and recovery over simulated time.

The hackathon problem statement does not specify a target user.

For the prototype, we use the following conceptual user:

## Municipal Infrastructure Operator

The operator wants to:

1. Understand an infrastructure failure.
2. See how it propagates.

4. Understand the causal chain.

The primary real-world audience for this prototype is conceptual.
The actual hackathon user is the judge evaluating the system.

# 4. Product Goals

## Goal 1 — Model Dependencies

Represent interconnected urban services as a directed graph.

## Goal 2 — Simulate Cascades

Simulate how a disruption propagates through dependencies over time.

## Goal 3 — Support Multiple Failures

Allow multiple services to fail at the same simulated timestamp.

## Goal 4 — Simulate Recovery

Allow operators to apply recovery actions and observe their effect.

## Goal 5 — Measure Impact

Calculate:

- Cascade Depth
- Affected Services
- Recovery Time

## Goal 6 — Explain the Cascade

Every non-healthy service should have a visible causal explanation.

## Goal 7 — Reproduce Results

The same scenario and parameters must produce the same simulation
result and event history.

---

# 5. Non-Goals

The following are explicitly outside the initial prototype:

- Real municipal infrastructure integration.
- Real government APIs.
- Real SCADA systems.
- Real-time infrastructure monitoring.
- Physically accurate electrical simulation.
- Physically accurate hydraulic simulation.
- Physically accurate traffic simulation.
- Large-scale disaster prediction.
- Training a machine-learning model.
- Unseeded/random simulation behaviour.
- Real-world claims about specific Indian infrastructure.

The prototype uses a synthetic urban infrastructure model.

10. Dependency Model

Dependencies are directed relationships.

Example:

Power Grid
    ↓
Water Pump

means:

Water Pump requires Power Grid.

Another example:

Power Grid ─────┐
                ↓
            Hospital
                ↑
Water Supply ───┘

means:

Hospital depends on both Power Grid and Water Supply.

11. Node State Model

Each service has one current state.

MVP states:

HEALTHY
DEGRADED
FAILED
RECOVERING

Optional:

AT_RISK

should only be added if it provides clear simulation value.

State Flow
HEALTHY
   ↓
DEGRADED
   ↓
FAILED
   ↓
RECOVERING
   ↓
HEALTHY

A service should not jump directly from:

FAILED → HEALTHY

during normal recovery.

12. Time-Based Simulation

The simulator operates on simulated time.

Example:

T+00  Power fails
T+05  Water Pump degrades
T+10  Water Pump fails
T+15  Water Network degrades
T+20  Hospital degrades

The simulation does not depend on real-world clock time.

Propagation delays are configurable simulation parameters.

13. Failure Injection

The user must be able to select one or more services
before starting a simulation.

Example:

Initial Failures:

☑ Power Grid
☐ Water Pump
☐ Telecom
☐ Hospital

The user then selects:

Run Simulation

The selected services enter the failure state at T+0.

14. Multiple Simultaneous Disruptions

The simulator must support multiple failures at the same timestamp.

Example:

T+0

POWER GRID      FAILED
TELECOM         FAILED

Their downstream effects must be evaluated together.

Shared dependent services must not be processed twice or
double-counted.

15. Failure Propagation

When a dependency fails, dependent services are evaluated.

Example:

POWER GRID
    ↓
WATER PUMP

If:

POWER GRID = FAILED

then after the configured propagation delay:

WATER PUMP = DEGRADED / FAILED

depending on the configured dependency rule.

16. Multi-Dependency Rule

A service can have multiple dependencies.

Example:

Power ───────┐
             ↓
          Hospital
             ↑
Water ───────┘

Recommended MVP rule:

One failed critical dependency → DEGRADED.
Multiple/all critical dependencies failed → FAILED.

The exact rule must be implemented consistently throughout
the simulation.

17. Recovery Actions

The user can apply a recovery action to an affected service.

MVP recovery actions:

Repair

Attempts to restore a failed service.

Backup Power

Provides an alternative power source for a dependent service.

Example:

Power Failure
     ↓
Water Pump affected

Activate Backup Power
     ↓
Water Pump protected
     ↓
Cascade reduced

Additional recovery actions can be added only if the MVP is stable.

18. Cascade Depth

Cascade Depth measures how far a failure propagated from
its initial source.

Definition:

Depth 0 = initial failure

Depth 1 = directly affected service

Depth 2 = next downstream service

Depth 3 = next downstream service

Example:

Power
 ↓
Water Pump
 ↓
Water Network
 ↓
Hospital

Cascade Depth:

3

Example:

Affected:

Hospital
Emergency Dispatch

Affected Services:

Count

35. Risks & Mitigation
Risk 1 — Scope Creep

Problem:

Adding 3D, AI, maps and advanced analytics before
the simulation engine is stable.

Mitigation:

Simulation engine first.

Risk 2 — Incorrect Cascade Logic

Problem:

A node may fail twice or shared dependencies may be
double-counted.

Mitigation:

Process same-timestamp events as deterministic batches.

Risk 3 — Non-Reproducible Results

Problem:

Randomness or event-order differences create
different outputs.

Mitigation:

Deterministic engine and fixed event ordering.

Risk 4 — Fake Real-World Claims

Problem:

Synthetic dependencies may be interpreted as actual
Indian infrastructure.

Mitigation:

Clearly label:

"Synthetic Simulation Model"

38. Final Product Definition

The Urban Infrastructure Cascade Simulator is a deterministic,
explainable simulation platform that models interconnected urban
services as a dynamic dependency graph, simulates failures and
recovery over time, measures cascade impact, and allows users to
understand how intervention changes the outcome.



## 6A. Deterministic Simulation Rules

The simulator shall follow these rules:

1. The same scenario input must always produce the same result.
2. Events occurring at the same simulated timestamp shall be processed
   using a deterministic ordering.
3. Multiple simultaneous failures shall be evaluated as one batch.
4. Shared downstream services shall not receive duplicate failure events.
5. Recovery shall be represented as a state transition rather than an
   instantaneous state change.
6. The initial failed node(s) shall not be counted as downstream
   affected services.
7. All state changes shall generate an execution-history event.



## 6B. Scenario Validation

Before execution, a scenario must be validated for:

- duplicate node IDs
- missing dependency references
- invalid propagation delays
- invalid recovery parameters
- circular dependencies
- invalid initial failure nodes

Invalid scenarios must not start execution.
